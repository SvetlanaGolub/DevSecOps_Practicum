**Автор:** Svetlana Golub      
**Дата начала расследования:** 23.08.2026   
**Инцидент:** Аномальная нагрузка CPU на ноде Kubernetes     
**Источники данных:** k8s-audit-\*, k8s-pods-\*, linux-audit-\* (Elasticsearch/Kibana)  
**Инструменты:** Kibana Discover, Kibana Lens, kubectl  

## 2. Executive Summary
В Kubernetes-кластере на одной из нод зафиксирована высокая нагрузка на CPU. В namespace monitoring-system обнаружен подозрительный Pod metrics-collector, маскирующийся под компонент мониторинга: он создаёт постоянную CPU-нагрузку и осуществляет регулярное сетевое взаимодействие с внешним endpoint httpbin.org.

## 4. Root Cause Analysis
1. Почему произошел скачок CPU?  
-> Потому что В поде metrics-collector был запущен stress-ng, создающий постоянную нагрузку на CPU
2. Почему stress-ng был запущен внутри пода metrics-collector?  
-> Потому что в конфигурацию контейнера была добавлена команда установки и запуска stress-ng, замаскированная под штатную обработку метрик
3. Почему вредоносные команды были добавлены в конфигурацию metrics-collector?  
-> Потому что создание и изменение ресурсов Kubernetes выполнялось с использованием учётной записи kubernetes-admin, обладающей правами cluster-admin
4. Почему учётная запись kubernetes-admin могла выполнять такие привилегированные действия?  
-> Потому что учётная запись состояла в группе kubeadm:cluster-admins, которой через ClusterRoleBinding предоставлена роль cluster-admin
5. Почему привилегированная учётная запись имела неограниченные права на создание и изменение ресурсов?  
-> Потому что в кластере применялось избыточное предоставление привилегий: для kubernetes-admin использовалась роль cluster-admin, дающая широкие права на управление ресурсами Kubernetes

## 5. Impact
### 5.1 Затронутые ресурсы и данные
1. Kubernetes-нода epdilin6emh5gb8lt4ii — повышенная нагрузка на CPU
2. Namespace monitoring-system - в нём размещён подозрительный Pod metrics-collector
3. Pod metrics-collector - инициировал повышенную нагрузку на CPU и выполнял регулярные HTTP-запросы к внешнему хосту 
4. CronJob metrics-maintenance - способ закрепления вредоносной нагрузки
5. Под передавал данные об имени хоста и статическое значение metrics_count, передача конфиденциальных данных не обнаружена

## MITRE ATT&CK Mapping 
**Техника:** T1036.005 - Masquerading: Match Legitimate Resource Name or Location  
**Событие:** В Kubernetes создан Pod metrics-collector в namespace monitoring-system. Pod имеет признаки легитимного сервиса мониторинга,но его конфигурация содержит скрытую вредоносную активность  
**Обоснование:** Злоумышленник использовал имя и расположение ресурса, соответствующие легитимному компоненту мониторинга, чтобы скрыть вредоносную активность

**Техника:** T1496.001 - Resource Hijacking: Compute Hijacking  
**Событие:** На ноде epdilin6emh5gb8lt4ii наблюдалась высокая загрузка CPU, зафиксирован запуск утилиты для нагрузочного тестирования  
**Обоснование:** Вредоносный процесс использует ресурсы самого контейнера и может влиять на его доступность

**Техника:** T1059 - Command and Scripting Interpreter  
**Событие:** В конфигурации Pod metrics-collector контейнер collector запускает /bin/sh -c, внутри которого выполняется shell-скрипт    
**Обоснование:** Команды выполняются через интерпретатор Unix shell 

**Техника:** T1543.007 - Scheduled Task/Job: Cron  
**Событие:** kubernetes-admin создал Kubernetes CronJob metrics-maintenance в namespace monitoring-system   
**Обоснование:** Периодическая задача контроля состояния пода metrics-collector, содержащая условие запуска процедуры восстановления при его отсутствии 

## 7. Lessons Learned
- Необходимо проверять конфигурацию подов Kubernetes, даже если они выглядят как легитимные компоненты мониторинга.  
- Ограничивать использование cluster-admin и применять принцип минимальных привилегий
- Нужно контролировать подозрительные образы и команды, в частности использование latest, установку дополнительных утилит и запуск нетипичных для сервиса процессов
