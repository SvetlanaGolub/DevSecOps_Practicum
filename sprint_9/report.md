## 1. Введение и краткое описание системы

В рамках практической работы проведена оценка угроз и рисков для банковского микросервиса, предназначенного для перевода средств между счетами и просмотра истории транзакций.

Архитектура приложения включает Backend API, базу данных PostgreSQL и кеш Redis.

В рамках работы выполнены:

- построение модели потоков данных (DFD);
- анализ угроз по методологии STRIDE;
- разработка контрмер для наиболее критичных угроз;
- статический анализ исходного кода с использованием Semgrep;
- обработка выявленных уязвимостей в DefectDojo.


## 2. Архитектура и предположения

### 2.1 Архитектура

Микросервис предоставляет HTTP/REST API для взаимодействия с пользователем.

Основные компоненты системы:

- **User** — пользователь, взаимодействующий с сервисом через API;
- **Backend API** — принимает и обрабатывает запросы пользователя;
- **PostgreSQL** — хранит данные приложения, включая данные счетов и транзакций;
- **Redis** — используется в качестве кеша.

Основные взаимодействия:

- User → Backend API — HTTP/REST;
- Backend API → PostgreSQL — SQL-запросы;
- Backend API → Redis — операции чтения и записи данных.

### 2.2 Предположения

При построении модели угроз приняты следующие предположения:

- пользователь взаимодействует с Backend API через HTTP/REST;
- Backend API является основной точкой входа в систему;
- данные, поступающие от пользователя, потенциально могут быть недоверенными;
- PostgreSQL содержит данные, связанные с банковскими операциями;
- Redis используется как внутренний компонент приложения;
- доступ к данным и операциям должен контролироваться на стороне Backend API.

### 3.2 Анализ угроз по STRIDE

На основе построенной DFD проведён анализ угроз с использованием методологии STRIDE.

| Угроза | Элемент DFD | STRIDE | Описание |
|---|---|---|---|
| Unauthorized user impersonation | Backend API | Spoofing | Атакующий может использовать скомпрометированные или поддельные учётные данные для обращения к Backend API от имени легитимного пользователя. |
| Unauthorized modification of database data |  PostgreSQL | Tampering | Атакующий может изменить данные в PostgreSQL через уязвимые операции API или недостаточную проверку входных данных. |
| Insufficient audit logging | Backend API | Repudiation | При отсутствии достаточного аудита пользователь может отрицать выполнение критической операции, а расследование инцидента будет затруднено из-за отсутствия необходимых записей. |
| Sensitive data disclosure | PostgreSQL | Information Disclosure | Компрометация API или недостаточное разграничение доступа может привести к раскрытию чувствительных данных, хранящихся в PostgreSQL. |
| Backend API resource exhaustion | Backend API | Denial of Service | Атакующий может отправлять большое количество запросов или создавать ресурсоёмкие операции, что приведёт к исчерпанию ресурсов приложения или Redis и нарушению доступности сервиса. |
| Privilege escalation through insufficient authorization | Backend API | Elevation of Privilege | Ошибка в механизме авторизации может позволить пользователю получить доступ к функциям или данным, предназначенным для пользователей с более высокими привилегиями. |

## 4. Критичные угрозы и контрмеры

Для разработки контрмер выбраны три наиболее критичные угрозы:

- **Unauthorized user impersonation (Spoofing)** — высокая критичность вследствие возможности получить доступ к Backend API от имени легитимного пользователя и выполнять несанкционированные операции.
- **Unauthorized modification of database data (Tampering)** — высокая критичность вследствие возможности нарушения целостности данных PostgreSQL и влияния на основные бизнес-операции сервиса.
- **Sensitive data disclosure (Information Disclosure)** — высокая критичность вследствие возможности раскрытия чувствительных данных пользователей и служебной информации.

Выбор обусловлен потенциальным воздействием угроз на конфиденциальность и целостность данных, а также на основные бизнес-процессы микросервиса.

| Угроза | Контрмера | Тип | Уровень применения |
|---|---|---|---|
| Unauthorized user impersonation (Spoofing) | Многофакторная аутентификация (MFA) | Техническая | Код / инфраструктура |
| | Безопасное управление сессиями и токенами | Техническая | Код |
| | Серверная проверка прав доступа для каждой защищённой операции | Техническая | Код |
| Unauthorized modification of database data (Tampering) | Параметризованные SQL-запросы | Техническая | Код |
| | Принцип минимальных привилегий для учётной записи приложения в PostgreSQL | Архитектурная | Инфраструктура |
| | Ограничения целостности, транзакции и резервное копирование | Техническая | Инфраструктура |
| Sensitive data disclosure (Information Disclosure) | Шифрование данных при передаче и хранении | Техническая | Инфраструктура |
| | Разграничение доступа к данным (RBAC/ABAC) | Архитектурная | Код / инфраструктура |
| | Минимизация хранимых и возвращаемых данных | Архитектурная | Код |

## 5. Процесс управления уязвимостями

### 5.1 SAST-сканирование

Для статического анализа исходного кода приложения был использован инструмент **Semgrep**. Сканирование выполнялось на виртуальной машине с Debian.

Для анализа использовались правила Semgrep для Python. Результаты сканирования были сохранены в формате JSON, поддерживаемом для последующего импорта в DefectDojo.

В результате сканирования была обнаружена уязвимость SQL Injection в файле app/crud.py:

**Файл:** app/crud.py  
**Строка:** 66  
**Тип:** SQL Injection  
**CWE:** CWE-89 — Improper Neutralization of Special Elements used in an SQL Command   

Semgrep определил использование конкатенации строк при формировании SQL-запроса. При попадании пользовательского ввода в формируемый таким образом запрос существует риск SQL-инъекции.

Результат сканирования сохранён в файле **semgrep_report.json** и импортирован в DefectDojo в рамках CI/CD Engagement.

Помимо автоматически обнаруженной SQL Injection, в DefectDojo вручную добавлена уязвимость IDOR (Insecure Direct Object Reference).

### 5.2 Workflow обработки уязвимости в DefectDojo

Жизненный цикл уязвимости состоит из следующих этапов:

1. **Обнаружение и импорт**
   - SAST-сканирование исходного кода выполняется с помощью Semgrep.
   - Результаты сканирования сохраняются в формате JSON.
   - JSON-файл импортируется в DefectDojo в рамках Engagement.
   - Уязвимость SQL Injection появляется в списке Findings.
   - Уязвимость IDOR добавляется вручную как отдельная находка.

2. **Триаж и приоритизация**
   - Для каждой находки анализируются тип уязвимости, затронутый компонент и потенциальное воздействие.
   - Проверяется корректность срабатывания.
   - При необходимости уточняются Severity, Impact, Mitigation и Steps to Reproduce.
   - После подтверждения уязвимости ей устанавливается статус Verified.
   - На основании критичности определяется приоритет исправления.

3. **Назначение ответственного**
   - Подтверждённая уязвимость передаётся команде разработки.
   - В DefectDojo для неё назначается ответственный разработчик.
   - Ответственный получает возможность просматривать находку, изменять её и обновлять статус.

4. **Исправление**
   - Разработчик устраняет уязвимость в исходном коде.
   - Например, SQL Injection устраняется использованием параметризованных SQL-запросов.
   - IDOR устраняется серверной проверкой прав доступа к запрашиваемому объекту.

5. **Повторная проверка**
   - После исправления выполняется повторное сканирование Semgrep либо ручная проверка.
   - Результат сравнивается с исходной находкой.
   - При необходимости в DefectDojo добавляются комментарии и доказательства исправления.

6. **Закрытие**
   - Если уязвимость действительно устранена и повторная проверка подтверждает исправление, находка переводится в статус Mitigated.
   - Если уязвимость не устранена, она остаётся открытой и возвращается на доработку.

7. **Отслеживание и отчётность**
   - DefectDojo сохраняет историю изменений, статусы, назначения и комментарии.
   - На основании этих данных формируются отчёты по найденным уязвимостям, их критичности и состоянию исправления.

## 6. Выводы и рекомендации

В рамках работы проведена оценка угроз и рисков банковского микросервиса на основе DFD и методологии STRIDE.
В результате анализа были выявлены угрозы, связанные с аутентификацией, целостностью и конфиденциальностью данных, аудитом, доступностью API и разграничением привилегий.
SAST-анализ с использованием Semgrep позволил выявить SQL Injection. Дополнительно в DefectDojo вручную была зарегистрирована уязвимость IDOR.

Для повышения уровня защищённости рекомендуется:
- использовать параметризованные SQL-запросы;
- обеспечить серверную проверку прав доступа для каждой защищённой операции;
- применять принцип минимальных привилегий;
- обеспечить достаточное журналирование критичных операций;
- регулярно выполнять SAST-сканирование и повторную проверку исправлений;
- использовать DefectDojo для централизованного учёта, приоритизации и контроля жизненного цикла уязвимостей.
