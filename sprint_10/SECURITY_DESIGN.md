# Моделирование угроз

Моделирование выполнено по методологии **STRIDE** и основано на текущей архитектуре и конфигурации приложения Spring PetClinic.

## 1. Схема развёртывания

Схема развёртывания представлена в формате drawio в корне проекта (PetClinic.drawio) и содержит следующие основные компоненты:

```text
             [User]
                |
                | HTTP/HTTPS
                v
    --- Trust Boundary ---
                |
             [Ingress]
                |
                | HTTP
                v
          [Web Backend]
           Spring Boot
                |
                | SQL
                v
           [Database]
            PostgreSQL
```

### Компоненты

- **User** — внешний пользователь приложения.
- **Ingress** — внешняя точка входа приложения, принимающая HTTP/HTTPS-трафик и передающая запросы Web Backend
- **Web Backend** — приложение Spring Petclinic на базе Spring Boot
- **Database** — PostgreSQL, используемый приложением для хранения данных
- **Trust Boundary** — граница доверия между внешним пользователем и внутренней частью приложения

## 2. Модель угроз STRIDE

Для выявления угроз рассматриваются следующие компоненты:

1. Внешний пользователь
2. Поток данных **User → Ingress**
3. Поток данных **Ingress → Web Backend**
4. Web Backend
5. Поток данных **Web Backend → Database**
6. Database

### 2.1. T1 — Отсутствие аутентификации и авторизации

**STRIDE:** Spoofing / Elevation of Privilege
**Компонент:** Web Backend
**Описание:** В проекте отсутствует механизм аутентификации и авторизации пользователей. В зависимостях приложения отсутствует Spring Security, а контроллеры предоставляют операции просмотра, создания и изменения данных без проверки личности и полномочий пользователя.  
**Воздействие:** Злоумышленник может получить доступ к функциям приложения и выполнять операции изменения данных без предварительной аутентификации.  
**Меры защиты:**
- добавить Spring Security
- реализовать аутентификацию пользователей
- определить роли и права доступа
- закрыть операции изменения данных от неаутентифицированных пользователей
- реализовать RBAC для различных типов пользователей
- вести журнал значимых действий пользователей

### 2.2. T2 — Broken Object Level Authorization (IDOR)

**STRIDE:** Elevation of Privilege / Information Disclosure  
**Компонент:** Web Backend  
**Описание:** Приложение использует идентификаторы объектов непосредственно в URL. При этом отсутствие полноценной авторизации означает, что доступ к объекту фактически определяется переданным идентификатором, а не правами текущего пользователя.  
**Воздействие:** Просмотр данных другого владельца, изменение данных другого владельца, изменение информации о чужих питомцах, добавление визитов к чужим питомцам  
**Меры защиты:**
- реализовать object-level authorization
- связывать пользователя с разрешёнными объектами
- проверять права доступа при каждом обращении к `ownerId` и `petId`
- не считать сам идентификатор достаточным основанием для доступа
- добавить автоматические тесты на попытки доступа к чужим объектам

### 2.3. T3 — Раскрытие служебной информации через Actuator

**STRIDE:** Information Disclosure  
**Компонент:** Web Backend  
**Описание:** Настройка в `application.properties` открывает все доступные Actuator endpoints через Web.Подобная настройка предназначена для development/testing и не должна использоваться в production.  
**Потенциальное воздействие:** Публичное предоставление служебных endpoints может раскрывать информацию о состоянии и конфигурации приложения и увеличивать поверхность атаки.  
**Меры защиты:**
- не использовать `management.endpoints.web.exposure.include=*` в production
- публиковать только необходимые endpoints
- ограничить доступ к management endpoints
- при необходимости вынести management endpoints на отдельный порт или сетевой интерфейс
- защитить чувствительные endpoints аутентификацией и авторизацией

### 2.4. T4 — Компрометация базы данных из-за credentials в конфигурации

**STRIDE:** Information Disclosure / Elevation of Privilege
**Компонент:** Database / Web Backend  
**Описание:**  Kubernetes-манифесте `k8s/postgres-statefulset.yaml` для PostgreSQL используются статические учётные данные.
**Потенциальное воздействие:** Компрометация учётных данных может привести к несанкционированному подключению к базе данных и чтению или изменению данных приложения.
**Меры защиты:** 
- не хранить реальные credentials в Git
- использовать Kubernetes Secrets совместно с внешним Secret Manager при необходимости
- использовать уникальные и сложные пароли
- регулярно ротировать credentials
- создать отдельную БД-учётную запись для приложения с минимально необходимыми правами
- ограничить сетевой доступ к PostgreSQL
- не публиковать порт `5432` наружу без необходимости
- обеспечить шифрование соединения с БД при передаче данных по недоверенной сети

### 2.5. T5 — Отказ в обслуживании приложения
**STRIDE:** Denial of Service  
**Компоненты:** Ingress / Web Backend / Database  
**Описание:** Kubernetes Deployment приложения настроен с одной репликой. В конфигурации Deployment также отсутствуют `resources.requests` и `resources.limits`. При большом количестве запросов злоумышленник может вызвать исчерпание ресурсов приложения или базы данных и сделать сервис недоступным.
**Потенциальное воздействие:** Ухудшение производительности, исчерпание CPU или памяти, увеличение времени ответа, недоступность Web Backend, повышенная нагрузка на PostgreSQL.
**Меры защиты:**
- задать `resources.requests` и `resources.limits`
- использовать несколько реплик приложения
- настроить Horizontal Pod Autoscaler
- реализовать rate limiting на внешней точке входа
- установить ограничения на размер запросов и время их обработки
- ограничить количество соединений с PostgreSQL
- настроить мониторинг CPU, памяти, количества запросов и времени ответа

## 3. Сводная таблица угроз
| Угроза | STRIDE | Компонент | Воздействие | Основная мера защиты |
|---|---|---|---|---|
| T1 - Отсутствие аутентификации и авторизации | Spoofing / Elevation of Privilege | Web Backend | Несанкционированный доступ и изменение данных | Spring Security, authentication, RBAC |
| T2 - BOLA / IDOR | Elevation of Privilege / Information Disclosure | Web Backend | Доступ к данным чужих объектов | Object-level authorization |
| T3 - Раскрытие информации через Actuator | Information Disclosure | Web Backend | Раскрытие служебной информации | Ограничение Actuator endpoints |
| T4 - Компрометация БД из-за credentials | Information Disclosure / Elevation of Privilege | Web Backend / Database | Компрометация данных БД | Secret Manager, credential rotation, least privilege |
| T5 - Отказ в обслуживании | Denial of Service | Ingress / Web / DB | Недоступность приложения | Rate limiting, resource limits, scaling |

## 4. Меры защиты

1. **Аутентификация и авторизация** — исключить несанкционированный доступ к функциям приложения.
2. **Object-level authorization** — исключить доступ пользователей к чужим владельцам и питомцам.
3. **Ограничение Actuator** — уменьшить внешнюю поверхность атаки и раскрытие служебной информации.
4. **Защита credentials PostgreSQL** — исключить использование статических учётных данных из репозитория.
5. **Защита от DoS** — настроить ограничения ресурсов, масштабирование и rate limiting.

## 6. Итог

Проведённое моделирование показало, что основные риски приложения связаны с контролем доступа, раскрытием служебной информации, защитой учётных данных PostgreSQL и устойчивостью приложения к чрезмерной нагрузке.

Наиболее приоритетными являются реализация аутентификации и авторизации, а также проверка прав доступа непосредственно на уровне объектов. Ограничение Actuator и защита credentials позволяют уменьшить вероятность раскрытия внутренней информации и компрометации базы данных.
