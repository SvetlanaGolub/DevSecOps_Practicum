## 4. Подтверждённые уязвимости

### 4.1 Server-Side Request Forgery (SSRF) в эндпоинте /fetch
**Класс:** SSRF  
**Статус:** valid  
**Риск:** Critical  
**CVSS v4.0:** 9.1 (AV:N/AC:L/AT:N/PR:N/UI:N/VC:H/VI:N/VA:H/SC:H/SI:N/SA:N)  
**Связь с OWASP:** OWASP Top 10 2025: Security Misconfiguration, OWASP API Security Top 10 2023: Server-Side Request Forgery.

**Описание** 
Эндпоинт `/fetch` принимает параметр `url` и передаёт его в функцию `requests.get()` без какой-либо валидации или фильтрации. Это позволяет злоумышленнику заставить сервер выполнить HTTP-запрос к любому адресу, включая внутренние сервисы.

**Метод обнаружения**  
Уязвимость обнаружена в ходе статического анализа кода. В функции `fetch()` параметр `url` передаётся в `requests.get()` без валидации, что является классическим признаком SSRF. Для подтверждения отправлен запрос к внутреннему ресурсу:
```
curl "http://127.0.0.1:5000/fetch?url=http://127.0.0.1:5000/notes/1"
```
Получен ответ от внутреннего сервиса, что доказывает возможность выполнения запросов к недоступным извне ресурсам.

**Шаги воспроизведения**  
1. Отправить GET-запрос к `/fetch` с параметром `url`, указывающим на внутренний ресурс:
```GET /fetch?url=http://127.0.0.1:5000/notes/1 HTTP/1.1
Host: 127.0.0.1:5000
```
2. Получение ответа от внутреннего сервиса, подтверждающее успешное взаимодействие.

**Ожидаемое поведение**  
Сервер должен отклонять запросы к внутренним адресам (localhost, частные IP-адреса) или использовать белый список разрешённых доменов.

**Фактическое поведение**  
Сервер выполняет запрос по указанному URL и возвращает ответ. При запросе `http://127.0.0.1:5000/notes/1` возвращается содержимое заметки пользователя. 

**Влияние**  
Уязвимость может быть эксплуатации без аутентификации, что делает её критически опасной:
- Сканирование внутренней сети и обнаружение сервисов
- Доступ к конфиденциальной информации (метаданные облачных провайдеров, внутренние API)
- Взаимодействие с внутренними службами (базы данных, Redis, Elasticsearch)
- Атаки на внутренние системы через другие протоколы

**Рекомендации**  
Внедрить строгую валидацию URL по белому списку, Проверять фактический IP-адрес после DNS-резолвинга, Настроить сетевые политики для ограничения исходящего трафика.

### 4.2 Reflected XSS в эндпоинте /hello
**Класс:** Reflected XSS  
**Статус:** valid    
**Риск:** High  
**CVSS v4.0:** 8.2 (AV:N/AC:L/AT:N/PR:N/UI:P/VC:H/VI:N/VA:N/SC:H/SI:N/SA:N)   
**Связь с OWASP:** OWASP Top 10 2025: Injection, OWASP WSTG Input Validation Testing: Reflected XSS. 

**Описание** 
Эндпоинт `/hello` принимает параметр `name` и вставляет его в HTML-ответ без какого-либо экранирования. Это позволяет злоумышленнику внедрить произвольный JavaScript-код, который будет выполнен в браузере при переходе по специально сформированной ссылке.

**Метод обнаружения**  
Уязвимость обнаружена при анализе кода: параметр `name` вставляется в ответ через f-строку без экранирования. Для подтверждения отправлен запрос с JavaScript-пэйлоадом:

```
curl "http://127.0.0.1:5000/hello?name=%3Cscript%3Ealert(%27XSS%27)%3C/script%3E"
```
В ответе получен HTML с тегом `<script>`, что подтверждает возможность выполнения кода в браузере жертвы.

**Шаги воспроизведения**  
1. Отправить GET-запрос к /hello с параметром name, содержащим JavaScript-код:
```
GET /hello?name=%3Cscript%3Ealert(%27XSS%27)%3C/script%3E
Host: 127.0.0.1:5000
```
2. Открыть полученную страницу в браузере
3. Выполнение JavaScript-кода - всплывающее окно с текстом "XSS"

**Ожидаемое поведение**  
Пользовательский ввод должен быть экранирован и отображаться как обычный текст. 

**Фактическое поведение**  
JavaScript-код вставляется в HTML-ответ как есть и выполняется в браузере, что подтверждает наличие XSS-уязвимости. Ответ сервера содержит:

```
<h1>Привет, <script>alert('XSS')</script>!</h1>
``` 

**Влияние**  
Может привести к краже сессионных cookies авторизованных пользователей, подмене содержимого страницы, выполнению действий от имени пользователя, перенаправлению на вредоносные сайты.  

**Рекомендации**  
Использовать функцию `escape()` из библиотеки markupsafe для экранирования пользовательского ввода, использовать систему шаблонов Jinja2, которая автоматически экранирует вывод, внедрить Content Security Policy (CSP) как дополнительный слой защиты

### 4.3 Insecure Direct Object Reference (IDOR) в эндпоинте `/notes/<int:note_id>`  
**Класс:** IDOR / Broken Object Level Authorization    
**Статус:** valid    
**Риск:** Medium 
**CVSS v4.0:** 6.5 (AV:N/AC:L/AT:N/PR:L/UI:N/VC:H/VI:N/VA:N/SC:N/SI:N/SA:N)   
**Связь с OWASP:** OWASP Top 10 2025: Broken Access Control, OWASP API Security Top 10 2023: Broken Object Level Authorization   

**Описание** 
Эндпоинт `/notes/<int:note_id>` возвращает содержимое заметки по её идентификатору без проверки, принадлежит ли эта заметка текущему пользователю. Хотя данные содержат поле `user_id`, оно не используется для авторизации запроса. Это позволяет любому авторизованному пользователю получить доступ к заметкам других пользователей, просто изменяя числовой идентификатор в URL.

**Метод обнаружения**  
Уязвимость обнаружена при анализе кода: в функции `get_note()` отсутствует проверка владельца объекта. Для подтверждения выполнены запросы:
```
# Заметка пользователя 1
curl "http://127.0.0.1:5000/notes/1"  
# Заметка пользователя 2
curl "http://127.0.0.1:5000/notes/2"  
```
Сервер вернул обе заметки, хотя пользователь с `user_id=1` не должен иметь доступ к заметке пользователя `user_id=2`.

**Шаги воспроизведения**  
1. В демонстрационном приложении функция `get_current_user_id()` всегда возвращает `1`, поэтому считаем, что текущий пользователь имеет `user_id=1`
2. Открыть свою заметку:
```
GET /notes/1 HTTP/1.1
Host: 127.0.0.1:5000 
```
1. Изменить идентификатор на заметку пользователя c `user_id=2`:

```
GET /notes/2 HTTP/1.1
Host: 127.0.0.1:5000
``` 

**Ожидаемое поведение**  
Сервер должен проверять, что `note["user_id"] ` соответствует `get_current_user_id()`, и возвращать ошибку `403 Forbidden` при несовпадении. Доступ к объектам должен быть строго ограничен их владельцами.

**Фактическое поведение**  
Сервер возвращает содержимое заметки без проверки прав доступа. При запросе `/notes/2` пользователь с `user_id=1` получает данные, принадлежащие пользователю с `user_id=2`.

**Влияние**  
Обычный авторизованный пользователь может читать чужие приватные данные. Нарушается конфиденциальность персональной информации. 

**Рекомендации**  
Проверять право доступа к объекту на сервере для каждого запроса чтения, изменения и удаления. Добавить тесты на горизонтальную эскалацию прав для API заказов. Рассмотреть использование UUID вместо числовых ID для затруднения подбора.
